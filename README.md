# Монітор вільних місць Hamzabeyli

Консольна програма перевіряє публічний API TirParklari, показує підтверджені вільні інтервали та зберігає історію. Вона не бронює місця і не вводить персональних даних.

## Встановлення та запуск

Потрібні Node.js LTS 22.15 або новіший (версії 22 чи 24) і npm. У CMD у папці проєкту:

```cmd
npm ci
copy .env.example .env
npm run once
```

У PowerShell для копіювання використовуйте `Copy-Item .env.example .env`. Наявний `.env` повторно копіювати не потрібно. Відредагуйте його у текстовому редакторі за потреби.

| Команда | Дія |
| --- | --- |
| `npm run once` | Одна перевірка всіх дат |
| `npm start` | Безперервний моніторинг усіх дат |
| `npm run watch:period` | Інтерактивний моніторинг дати та періоду |
| `npm run bot` | Telegram-бот і спільний монітор |
| `npm test` | Тести без мережевих запитів |
| `npm run build` | Перевірка типів TypeScript |

Моніторинг зупиняється за Ctrl+C. У безперервному режимі після першого показу результати виводяться лише при зміні списку, дат або повноти перевірки; деталі потрапляють до журналу. Зміни кількості та доступності порівнюються лише для достовірно перевірених дат у двох послідовних циклах. Після помилки чи невідомого стану повідомлення про зміну потребує двох нових порівнюваних результатів. Після перезапуску поточний список показується знову, а збережена історія не створює повторну подію тільки через показ.

## Дати й період

За підтвердженим користувачем правилом сайт показує сьогоднішній день у Туреччині та три наступних. Програма обчислює дати у `Europe/Istanbul` кожного циклу. Кількість днів налаштовується через `FALLBACK_DAYS`, за замовчуванням 4; значення, відмінне від 4, може не відповідати сайту. Старі `DATE_DISCOVERY_MODE` і `FALLBACK_DATES` більше не впливають на вибір дат; за наявності `FALLBACK_DATES` записується повідомлення в журнал.

У `watch:period` введіть дату `DD.MM.YYYY` із поточного вікна і період `HH:mm-HH:mm`. Показуються вільні інтервали, які хоча б частково перетинаються із заданим періодом: наприклад, `20:01-20:02` включає інтервал `20:00–20:30`, а `14:01-21:45` — інтервали від `14:00–14:30` до `21:30–22:00`. Дотик лише на межі не вважається перетином: `14:00-14:30` не включає `13:30–14:00` чи `14:30–15:00`. `24:00` дозволено тільки як кінець. Режим запитує лише обрану дату і завершується, коли період минув або дата вийшла з вікна.

Інтервали, що вже почалися за турецьким часом, не показуються: можливість запису на них не підтверджена. Перевірте системний годинник комп'ютера. Час переходу інтервалу в минуле не є подією зникнення місць.

## Налаштування

| Змінна | Типове значення | Призначення |
| --- | --- | --- |
| `PARK` | `hamzabeyli` | Підтримувана стоянка |
| `POLL_INTERVAL_SECONDS` | `60` | Пауза після успішного циклу |
| `PERIOD_POLL_INTERVAL_SECONDS` | `1` | Інтервал циклів Telegram-відстеження періодів |
| `REQUEST_TIMEOUT_SECONDS` | `10` | Таймаут запиту |
| `REQUEST_DELAY_MS` | `1000` | Пауза між датами |
| `FALLBACK_DAYS` | `4` | Кількість днів від поточного дня в Туреччині |
| `VERBOSE` | `false` | `true` або `1` додатково виводить діагностику |

Запити виконуються послідовно: один на дату за цикл, з максимум двома повторними спробами при тимчасових помилках. Чотири дні означають до чотирьох запитів плюс можливі повтори; режим періоду — один плюс повтори. Інтервал 60 секунд не є підтвердженим дозволом сайту на таку частоту. При помилках пауза між циклами збільшується; HTTP 429 зупиняє цикл і викликає паузу не менше п'яти хвилин або довшу згідно з `Retry-After`. При HTTP 401/403 чи не-JSON відповіді програма завершується без обходу захисту.

## Правила та файли

Підтверджений доступний інтервал має `kalan > 0`, `acik=true`, `kapali=false`; зайнятий — `kalan=0`, `acik=false`, `kapali=false`. Інші комбінації залишаються невідомими, записуються в діагностичний журнал і не перезаписують достовірний стан. У дослідженому публічному JavaScript сайту `kapali` та `acik` перевіряються окремо; це не підтверджує універсального значення усіх комбінацій. Помилка API, невідомий стан або відсутній у відповіді інтервал не вважаються зникненням. При неповних даних програма показує попередження, а не стверджує, що вільних місць немає.

- `data/state.json` — останні достовірні стани, записані через тимчасовий файл і перейменування. Якщо файл пошкоджений, програма зупиниться без його перезапису. Збережіть копію та відновіть справний файл або вручну перенесіть пошкоджений файл, щоб почати спочатку.
- `data/available_slots.txt` — історія нових і повторних появ та підтверджених збільшень кількості (`AVAILABLE_INCREASE`). Причина збільшення API не повідомляється.
- `logs/monitor.log` — діагностика, помилки, невідомі стани і зміни кількості.

Знімок термінала формується з актуальних відповідей, а стан і історія зберігаються окремо. Фільтр періоду не позначає інші інтервали зайнятими. Оскільки файли стану та історії записуються окремими операціями, аварійне завершення між ними може призвести до пропуску запису події.

## Якщо є помилка TLS

Команди монітора автоматично використовують системне сховище довірених сертифікатів Node.js (`--use-system-ca`). Окремо встановлювати `NODE_OPTIONS` не потрібно; перевірка TLS залишається увімкненою. При `UNABLE_TO_VERIFY_LEAF_SIGNATURE` та інших помилках сертифіката програма зупиняється і повідомляє про проблему. Якщо помилка зберігається, перевірте дату й час, мережевий проксі та довірені сертифікати з адміністратором; сервер також може надавати неповний ланцюжок сертифікатів.

Збережений приклад відповіді `tests/fixtures/2026-11-04.json` є історичним і використовується лише в тестах.

## Telegram-бот

Бот працює через grammY та long polling і потребує запущеного процесу Node.js на увімкненому комп'ютері або сервері. Підтримуються лише приватні чати. Токен надає BotFather; не вставляйте його в код, журнал або повідомлення іншим людям. Якщо токен випадково розкрито, відкличте його через BotFather і створіть новий.

1. Встановіть залежності за допомогою `npm ci`. Якщо `.env` ще немає, створіть його командою `copy .env.example .env` у CMD.
2. Відкрийте `.env` у редакторі та задайте `TELEGRAM_ENABLED=true` і `TELEGRAM_BOT_TOKEN=ваш_токен`. Не додавайте лапки, якщо вони не є частиною токена.
3. Запустіть `npm run bot`, знайдіть свого бота в Telegram і надішліть `/start`. Завершуйте процес через Ctrl+C. Якщо ви змінюєте `.env`, перезапустіть процес.
4. Для тестової перевірки натисніть «🔍 Перевірити місця», створіть відстеження, відкрийте «📋 Мої відстеження» і видаліть його після перевірки. Команди `/menu` та `/cancel` повертають до меню і скасовують незавершене введення.

Файл має називатися саме `.env`, а не `.env.example` чи `.env.txt`, і лежати поруч із `package.json`. У ньому потрібен рядок `TELEGRAM_BOT_TOKEN=ваш_токен`: самого токена без назви змінної недостатньо. Збережіть файл у UTF-8. Якщо у вікні CMD раніше задали порожню змінну з таким іменем, вона має пріоритет над `.env`: відкрийте новий термінал або виконайте `set TELEGRAM_BOT_TOKEN=` у CMD (у PowerShell — `Remove-Item Env:TELEGRAM_BOT_TOKEN -ErrorAction SilentlyContinue`). Не публікуйте токен під час діагностики.

«🌍 Відстежувати всі дні» створює одне загальне відстеження на користувача. «📅 Відстежувати період» запитує дату й час та створює відстеження тільки після підтвердження. Можна створити кілька періодів, включно з майбутніми датами поза поточним вікном: бот почне перевірку автоматично, коли дата увійде у вікно і API поверне підтверджену відповідь. «📋 Мої відстеження» дозволяє переглянути, видалити після підтвердження та перемикати гучні повідомлення для окремого періоду. Тут також показуються повідомлення з невизначеним результатом доставки, якщо вони є.

**Правило Telegram-періоду:** на відміну від консольної команди `watch:period`, у Telegram показуються лише інтервали, які повністю входять у вибраний період. Наприклад, `18:15-20:00` не включає `18:00–18:30`. Інтервали, що вже почалися, не показуються. Завершені періоди автоматично видаляються; загальне відстеження діє до ручного видалення. Повідомлення про початковий стан не змінюється. Повідомлення про подальшу зміну стосується одного інтервалу; після успішного надсилання нового бот намагається видалити попереднє для того самого відстеження й інтервалу. Згідно з [Telegram Bot API](https://core.telegram.org/bots/api#deletemessage), звичайне видалення має обмеження за віком повідомлення, зокрема 48 годин.

Гучні повідомлення вмикаються окремо для періоду. Вони надходять додатково при появі або збільшенні кількості місць; події одного циклу об'єднуються. Telegram і телефон визначають звук та гучність: бот не обходить беззвучний режим. У налаштуваннях повідомлень конкретного чату Telegram можна вибрати окремий звук, якщо клієнт його підтримує.

Додаткові змінні `.env`:

| Змінна | За замовчуванням | Призначення |
| --- | --- | --- |
| `TELEGRAM_ENABLED` | `true` | Дозволити команду `npm run bot` |
| `TELEGRAM_BOT_TOKEN` | порожньо | Токен бота, потрібний лише для `npm run bot` |
| `DATABASE_PATH` | `./data/monitor.db` | Шлях до SQLite |
| `LOG_RETENTION_DAYS` | `30` | Термін зберігання ротованих логів |
| `DEFAULT_URGENT_NOTIFICATIONS` | `false` | Початкове значення гучних повідомлень для нових періодів |

SQLite зберігає користувачів і chat ID (`users`), відстеження (`trackings`), останні стани (`slot_states`), ідентифікатори повідомлень (`notification_messages`) та чергу доставки (`deliveries`). Для бази увімкнено foreign keys і WAL; схема версіонується через `user_version`. `node:sqlite` може виводити експериментальне попередження на деяких версіях Node.js 22. Для резервної копії зупиніть бота й скопіюйте `monitor.db` разом із `monitor.db-wal` і `monitor.db-shm`, якщо ці файли існують. `.env`, база, тимчасові файли бази та `logs/` виключені з Git.

`logs/monitor.log` містить діагностику спільних запитів та системні помилки; `logs/users.log` — дії користувачів і результати доставки. Логи ротуються за датою; ротовані файли очищуються після `LOG_RETENTION_DAYS` днів під час запуску та щодня. Токен і приватні заголовки не записуються.

Бот отримує кожну необхідну дату один раз за спільний цикл, повторно використовує короткочасний кеш і порівнює результати окремо для кожного відстеження. Запускайте **один екземпляр `npm run bot`** на одну базу й одного бота: між окремими процесами блокування спільного циклу не реалізоване. `npm start` є окремим консольним монітором; одночасний запуск із ботом створює додаткові запити до сайту, тому рекомендовано використовувати один із них. Консольні команди не потребують Telegram-токена і зберігають окремий JSON-стан.

Telegram-відстеження періоду перевіряється за замовчуванням щосекунди (`PERIOD_POLL_INTERVAL_SECONDS=1`); загальне відстеження використовує `POLL_INTERVAL_SECONDS`. Для однакової дати в одному циклі виконується один спільний запит, а кеш для періодів живе не довше їхнього інтервалу. Тривалі запити, кілька дат, `REQUEST_DELAY_MS`, повторні спроби чи обмеження сервера можуть збільшити фактичну паузу. Одна дата за секунду означає приблизно 60 запитів за хвилину; дозволена сайтом частота не підтверджена. При помилках опитування сповільнюється, а при HTTP 429 зберігається пауза щонайменше п'ять хвилин або довша згідно з `Retry-After`.

Черга повідомлень зберігається до доставки. При явному Telegram 429 вона чекає `retry_after`. Коли результат надсилання невідомий через обрив або аварію, Telegram не надає ключа ідемпотентності для `sendMessage`: бот залишає запис `UNCERTAIN` і не повторює його автоматично, щоб не створити прихованих дублікатів. Користувач може явно повторити такі повідомлення через «📋 Мої відстеження», усвідомлюючи можливий дублікат. Це компроміс, а не гарантія одноразової доставки. Якщо повідомлення вже надсилається в момент видалення відстеження, бот намагається прибрати його після відповіді Telegram; повністю скасувати мережевий запит, уже прийнятий Telegram, неможливо. Незавершене введення форми зберігається в пам'яті та після перезапуску починається заново.
